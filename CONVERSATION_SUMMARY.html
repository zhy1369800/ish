Phase 1

需求诞生：外部通知驱动 Agent 与按需保活

用户最初提问：想要开发一个外部 Agent App，当收到特定通知事件时自动触发 iOS 快捷指令，在 iSH 终端中静默执行脚本或命令，并希望用无声音频进行后台保活。

核心共识：

  • 保活必须是“有任务才开，无任务/结束就关”，极致省电，不影响日常待机。
  • 采用音频混音模式（MixWithOthers），音量调至微弱/静音，不抢占音乐、播客或电话。
  • 纯自用，不上架 App Store，因此可以使用 iOS 后台音频权限作为保活抓手。
Phase 2

架构实现：十个核心模块构建

AudioKeepAliveManager
内存中生成 44 字节 PCM 无声 WAV，引用计数管理，电话/中断激进恢复。
CommandRunner
独立分配 /dev/pts/N 虚拟终端，fork init_child，SIGKILL 超时截杀与 stdout 收集。
RunCommandIntent.swift
iOS 16 AppIntents，设置 openAppWhenRun = false，实现无感静默后台执行。
/dev/keepalive 虚拟设备
注册主设备号 240、次设备号 2，使 Alpine Linux Shell 能直接 echo 1/0 控制宿主机保活。
URLHandler
支持 ish://run 异步调用及标准 ish://x-callback-url/run 成功/失败全自动回调响应。
Phase 3

深度代码审查与质量加固

第一轮修复 (4 个关键问题)：

1. Swift 桥接拼写修复；2. 音频停止竞态双重校验；3. PID 1 冷启动 5 秒轮询重试；4. 超时处理加入 SIGKILL 强杀防止僵尸进程。

第二轮审查与决议：

1. 移除 Intent 上的 @MainActor，与 UI 主线程彻底解耦；2. 补全 do_execve 极端失败路径下的孤儿 task 释放；3. 确认保持激进中断恢复策略以获得更强保活。

Phase 4

核心理论突破：Tmux 作为“进程间共享黑板”

关键质疑：快捷指令每次通过 become_new_init_child() 在新的独立子进程里跑命令，Tmux 怎么跨越进程拿到结果？

Tmux Client-Server 通信原理
[Linux Kernel PID 1]
   │
   ├── 常驻守护服务: 【tmux server】 (PID 120)
   │     ├── 管理终端虚拟屏幕缓冲区 (Screen Buffer)
   │     └── 运行长任务: python run_task.py (输出打在缓冲区中)
   │
   ▲
   │ 跨进程 Unix Domain Socket (/tmp/tmux-0/default)
   ▼
   │
   └── 快捷指令每次调用的轻量子进程 (PID 350)
         ├── 充当“遥控器 (tmux client)”
         ├── tmux send-keys: 告诉 server 敲入命令
         └── tmux capture-pane: 向 server 索取屏幕字符并输出
核心结论： tmux server 本质上是进程间共享的“公共黑板”。无论外部有多少个独立子进程，大家都通过同一个本地 Socket 读写黑板，实现命令注入与抓屏决策闭环。
Phase 5

实战命令宝典

1. 快捷指令派发长任务（带独立保活黄金模板）：
tmux send-keys -t agent "echo 1 > /dev/keepalive && python run_task.py; echo 0 > /dev/keepalive" C-m
2. Agent 无感抓屏（读取最近 100 行）：
tmux capture-pane -t agent -p -S -100
3. 检测长任务是否执行完毕（如果是 sh/ash 代表已完结）：
tmux display-message -t agent -p '#{pane_current_command}'
4. 前台人工介入与后台脱离：
tmux attach -t agent
# 退出查看并保持后台运行: 按下 Ctrl + b，松开后按 d
